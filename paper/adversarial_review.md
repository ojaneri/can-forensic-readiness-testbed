# Adversarial Review — IEEE/SSV Paper Draft

Target: `paper/article_ieee.html`

Reviewer stance: skeptical SSV/IEEE reviewer evaluating novelty, scientific validity, reproducibility, formatting, and risk of overclaiming.

## Executive Verdict

The paper has a promising practical artifact, but in its current form it is **not yet submission-ready**. The strongest contribution is the reproducible software-defined CAN evidence workflow. The weakest points are: synthetic-only validation, over-reliance on a trivial rule-based detector, incomplete references, lack of comparison against existing tools/datasets, and insufficient methodological detail for reproducibility.

Recommended positioning:

> This is not an IDS paper. It is a reproducible educational and forensic-readiness CAN testbed paper.

If the paper keeps this positioning, it can be credible. If it is framed as detection performance or realistic automotive attack evaluation, it becomes vulnerable.

---

## Critical / Potential Rejection Risks

### 1. The detector results look too good and may be considered trivial

Current claim:

- Accuracy: `0.9984`
- Macro-F1: `0.9982`

Problem:

The rules are almost directly aligned with how the synthetic data was generated:

- spoofing uses speed `180–200 km/h`;
- rule says speed `>130 km/h` = spoofing;
- flooding uses randomized IDs;
- rule says high ID cardinality/unknown ratio = flooding.

A reviewer may say this is circular validation, not a meaningful detection result.

Fix:

- Rename the detector from “baseline model” to **sanity-check forensic triage heuristic**.
- Move the metric from a central result to a supporting validation.
- Add a sentence: “The rule-based triage is not intended as a generalizable IDS baseline.”
- Add harder negative windows: high-speed legitimate event, bursty normal traffic, and normal traffic with extra IDs.

Suggested rewrite:

> The triage heuristic is used to validate label consistency and demonstrate explainable forensic screening, not to benchmark real-world intrusion detection.

---

### 2. Synthetic dataset may be seen as scientifically weak

Problem:

The dataset is fully generated by the same scripts used to define labels and semantics. There is no external validation, no real CAN trace comparison, no ICSim comparison, no ROAD/can-train-and-test replay, and no hardware-in-the-loop run.

Reviewer attack:

> Why is this more than a toy simulator?

Fix:

Add at least one of these before submission:

1. replay a public CAN dataset sample through the same logger;
2. run ICSim traffic and capture it with the logger;
3. compare generated traces to ROAD/can-train-and-test structurally;
4. add a small SocketCAN/vcan run on Linux with `can-utils` if possible;
5. add a table comparing the testbed with VitroBench, CANBench, ROAD, can-train-and-test, and ICSim.

Minimum acceptable fix:

- Add a **Comparison Table** and explicitly state the artifact is educational/forensic-readiness, not real-vehicle fidelity.

## Major Technical Issues

### 6. Inter-arrival time statistics appear contaminated

Dataset summary currently includes impossible/odd values such as negative inter-arrival time and very large max intervals. This likely happened because the combined dataset computes inter-arrival per phase across multiple experiments or discontinuous timestamps.

Risk:

If included, a reviewer will question data processing correctness.

Fix:

- Recompute inter-arrival time per `experiment_id + phase + arbitration_id` or per continuous time window.
- Do not report current inter-arrival values until fixed.
- Keep entropy and phase counts, which are safer.

---

### 7. Figures need publication polish

Problems:

- Speed plot lacks phase shading/markers.
- ID cardinality plot needs axis labels and clearer phase boundaries.
- Confusion matrix is visually acceptable but may be redundant with Table II.
- Architecture figure is good for draft but needs IEEE compactness.

Fix:

- Add shaded phase regions: baseline, spoofing, flooding, recovery.
- Add axis labels and units.
- Use grayscale/print-safe colors.
- Reduce figure count if 6-page limit is tight.

Priority figures:

1. Architecture.
2. Speed over time with phase shading.
3. ID diversity or confusion matrix — not both if space is tight.

---

### 8. The HTML is not a true IEEE template

Problem:

The HTML mimics IEEE style but is not the official IEEE LaTeX/DOCX template. For SSV/IEEE CPS, final submission will likely need PDF generated from official IEEE format.

Risk:

Layout may fail page limits, margins, font sizes, column balancing, or reference formatting.

Fix:

- Keep HTML for preview.
- Create an official IEEE LaTeX version using `IEEEtran`.
- Use `\documentclass[conference]{IEEEtran}`.
- Verify page count against 6-page limit.

## Medium Issues

### 9. Abstract is too dense and may overemphasize metrics

Problem:

The abstract includes many numbers and detector metrics. This can make reviewers focus on IDS performance instead of testbed contribution.

Fix:

Move detector metrics later or soften them:

> As a consistency check, a simple rule-based triage heuristic classified labeled windows with high accuracy in the generated dataset.

---

### 10. Related work lacks explicit gap analysis

Problem:

The related work lists categories but does not strongly contrast the proposed work.

Fix:

End Section II with a paragraph:

> Existing work provides realistic HIL benches, public IDS datasets, and CAN attack tools. However, fewer artifacts combine software-only reproducibility, explicit forensic evidence preservation, observer-safe demonstration, and low-cost educational deployment. This paper targets that intersection.

---

### 11. The forensic claim needs more rigor

Problem:

“Forensic analysis” is claimed, but the paper mostly shows logging and hashing. Real forensic readiness also involves acquisition process, chain of custody, time synchronization, tool validation, evidence handling, and interpretation limits.

Fix:

Rename some claims from “forensic analysis” to “forensic-readiness workflow” or “preliminary forensic triage.”

Add a table:

| Forensic requirement | Implemented artifact |
|---|---|
| Repeatability | experiment script + seed |
| Traceability | input plan + manifest |
| Integrity | SHA-256 hashes |
| Normalization | CSV data dictionary |
| Interpretation boundary | limitations section |

---

### 12. The paper needs an artifact availability statement

Add a short section or paragraph:

> The dataset, scripts, figures, and printable article draft are available through the project index. The observer demo is client-side only and replays stored artifacts.

If publishing publicly later, replace internal URL with GitHub/Zenodo.
